# 模型路由候选账号分时段并发配置实施方案

> 状态：Final — user approved  
> 版本：v1.0  
> 日期：2026-08-18  
> 变更摘要：新增模型路由候选账号的每日分时段并发配置、Redis 当前值刷新、全量立即刷新和多实例互斥执行能力。

## 1. 背景与目标

当前系统通过 `group_model_route_accounts.max_concurrency` 支持模型路由候选账号的固定最大并发限制。新需求是允许管理员为单个“分组 + 路由别名 + 候选账号”配置每日循环的分时段最大并发数。

目标：

- 不修改 `group_model_route_accounts` 表结构、数据和既有逻辑。
- 新增独立的分时段配置表，初始为空。
- 时间精确到分钟，采用每日循环。
- 时间段采用前闭后开，禁止重叠。
- 时间段可以不覆盖全天；未覆盖时间使用旧字段的默认值。
- 分时段并发允许具体正整数或 `unlimited`。
- 用户请求路径不计算时间、不查询分时段数据库。
- 支持页面编辑和全量立即刷新。
- 多实例下同一时刻只允许一个节点执行刷新任务。

非目标：

- 不支持按具体日期、星期、节假日配置。
- 不校验不同候选分时段并发数的账号级资源分配合理性。
- 不改变账号自身已有的全局并发限制。

## 2. 假设与已确认决策

- 使用系统时区，默认 `Asia/Shanghai`。
- 新表无数据时，系统行为与现有版本完全一致。
- `group_model_route_accounts.max_concurrency` 继续作为旧逻辑的默认值。
- 未命中任何分时段时，后台刷新任务使用旧字段的值。
- `unlimited` 继续使用现有字符串表示；数据库中可用 `NULL` 表示不受限。
- 不做账号级并发总和校验，也不要求分时段值小于旧默认值。
- 页面保存按候选整体替换全部时间段，避免逐行保存产生中间状态。
- 定时刷新和立即刷新使用同一把 Redis 刷新锁。
- 立即刷新抢锁成功后立即开始；已有任务时直接返回“刷新任务正在执行”，不排队。
- 任务完成后，下一次定时刷新在任务完成后的下一个整分钟 `00` 秒执行。
- 版本号不是第一版必需机制；通过单任务互斥和串行刷新避免并发覆盖。

## 3. 功能设计

### 3.1 候选账号页面

在现有候选账号最大并发配置项下方增加“分时段并发配置”区域。

页面支持：

- 新增、编辑、删除时间段。
- 选择分钟级开始时间和结束时间。
- 配置具体并发数或“不受限”。
- 显示“未配置分时段，使用默认最大并发”。
- 保存时拒绝时间段重叠。

时间规则：

```text
09:30~20:30 表示 09:30 <= 当前时间 < 20:30
```

页面显示 `HH:mm`，后端内部使用分钟数：`00:00=0`、`24:00=1440`。

### 3.2 分时段配置表

新增表：`group_model_route_account_concurrency_schedules`。

| 字段 | 类型 | 可空 | 说明 |
|---|---|---:|---|
| `id` | BIGINT | 否 | 主键 |
| `group_id` | BIGINT | 否 | 分组 ID |
| `route_alias` | VARCHAR(255) | 否 | 路由别名 |
| `account_id` | BIGINT | 否 | 候选账号 ID |
| `start_minute` | SMALLINT | 否 | `0~1439` |
| `end_minute` | SMALLINT | 否 | `1~1440` |
| `max_concurrency` | INT | 是 | 空值表示 `unlimited` |
| `created_at` | DATETIME(6) | 否 | 创建时间 |
| `updated_at` | DATETIME(6) | 否 | 更新时间 |

约束：

- `start_minute < end_minute`。
- 同一候选的时间段不能重叠。
- 同一候选不能存在重复时间段。
- 分时段并发为正整数或空值，不做账号级总和合理性校验。
- 初始迁移不回填任何旧数据。

### 3.3 有效并发计算

后台刷新时，对配置了分时段的候选计算当前值：

```text
当前分钟命中分时段：使用分时段值
当前分钟未命中：使用 group_model_route_accounts.max_concurrency
```

没有任何分时段配置的候选不参与新逻辑，继续走旧逻辑。

## 4. Redis 与请求路径

### 4.1 旧 key

保留现有 key 及值格式：

```text
concurrency:route-config:{route-key}
```

值为数字字符串或 `unlimited`。分时段调度任务不覆盖该 key。

实际并发槽位 key 也保持不变：

```text
concurrency:route:{route-key}
```

### 4.2 新 key

仅为配置过分时段的候选新增：

```text
concurrency:route-schedule:{route-key}
```

使用 Redis Hash，至少包含：

```text
limit
updated_at
```

`limit` 支持数字字符串或 `unlimited`。

新 key 可设置较长 TTL 作为异常清理保护；正常刷新会重新写入并续期。删除候选分时段配置时主动删除该 key。

### 4.3 请求读取

请求路径不做时间计算，不查询新配置表。通过一次 Redis Lua 或 Pipeline 完成：

```text
优先读取 schedule key 的 limit
如果新 key 不存在，读取旧 route-config key
```

新 key 暂时缺失时临时回退旧 key；两个 key 都缺失时沿用原有数据库兜底逻辑。

随后继续执行既有流程：

```text
AcquireRouteSlot
→ AcquireAccountSlot
→ 请求上游
```

没有分时段配置的候选不会创建新 key，行为与旧版本一致。

## 5. 刷新任务与多实例互斥

### 5.1 全局刷新锁

所有实例共用：

```text
concurrency:route-schedule:refresh-lock
```

抢锁使用随机 token 和 TTL：

```text
SET key random_token NX PX 300000
```

默认配置：

```yaml
gateway:
  model_route_schedule:
    # 刷新锁初始有效期
    refresh_lock_ttl_seconds: 300
    # 刷新任务执行期间的续租周期
    refresh_lock_renew_interval_seconds: 30
```

执行期间续租必须校验 token。释放锁时也必须校验 token，防止误删其他实例的新锁。

### 5.2 定时刷新

所有实例每分钟整点尝试抢锁：

```text
抢到锁：执行全量刷新
未抢到锁：跳过本轮
```

刷新完成后不补执行错过的历史轮次。若任务跨过一个或多个整分钟，下一次由之后的整分钟触发。

### 5.3 全量刷新内容

刷新任务：

1. 批量读取分时段配置表。
2. 计算所有配置了分时段的候选当前有效值。
3. 通过 Redis Pipeline 批量更新新 Hash。
4. 清理已删除分时段配置的运行时 key。
5. 记录成功、跳过和失败数量。

没有分时段配置的候选不写新 key，也不改变旧 key。

## 6. 立即刷新

立即刷新与定时刷新使用同一把锁：

```text
抢锁成功：立即执行全量刷新
抢锁失败：返回“刷新任务正在执行”
```

立即刷新不排队、不追加 pending 任务。

定时任务和立即刷新同时触发时，先抢到锁的执行，另一个跳过或返回执行中。

立即刷新完成后，下一次定时刷新按完成时间后的下一个整分钟计算。例如：

```text
10:00:20 开始
10:01:40 完成
下一次定时刷新：10:02:00
```

建议接口抢锁成功后返回任务已开始和任务 ID，不让 HTTP 请求长时间等待全量刷新完成；任务结果通过日志和运行状态查看。

## 7. API 与权限

建议增加以下管理接口，具体路径沿用现有 admin group 路由规范：

- 查询某分组下候选的分时段配置。
- 整体替换某个候选的全部分时段配置。
- 触发全量立即刷新。

分时段配置使用分组管理权限；全量刷新使用运维或分组管理权限。

整体替换请求示例：

```json
{
  "route_alias": "test-zlx",
  "account_id": 100,
  "schedules": [
    {
      "start": "09:30",
      "end": "20:30",
      "max_concurrency": 50
    }
  ]
}
```

## 8. 日志与可靠性

每次刷新记录：

- `task_id`
- 触发类型：`scheduled` 或 `manual`
- 实例 ID
- 开始时间、结束时间、耗时
- 候选总数、更新数、失败数
- 具体失败的 route key 和错误原因

失败处理：

- 保留上一次成功的 Redis 当前值。
- 续租失败时停止继续写入。
- 锁过期后其他实例可以接管。
- 下一轮定时刷新继续修复。

## 9. 兼容与回滚

- 旧表不改结构、不改数据、不迁移。
- 新表为空时旧行为完全不变。
- 旧版本只读取旧 Redis key，忽略新 key。
- 新版本新 key 缺失时回退旧 key。
- 启用功能前应先升级所有网关实例，否则旧实例不会执行分时段限制。
- 删除分时段配置并清理新 key 后即可恢复旧逻辑。

## 10. 验证策略

### 单元测试

- 前闭后开边界。
- `00:00`、`24:00` 转换。
- 时间段重叠拒绝。
- 时间段不覆盖全天。
- 未覆盖时间回退旧默认值。
- 数字并发值和 `unlimited`。
- 没有分时段配置时使用旧逻辑。

### 集成测试

- 新表为空时现有模型路由测试全部保持通过。
- 新 key 存在时优先使用新值。
- 新 key 缺失时回退旧 key。
- Redis 配置 key 和实际槽位 key 不混淆。
- 多实例同时刷新只有一个实例执行。
- 立即刷新与定时刷新不会重叠。
- 刷新任务跨分钟后不会补历史任务。
- 锁续租、锁释放和实例宕机接管。

### 验收标准

- 候选页面可在默认最大并发下配置分时段并发。
- 时间段精确到分钟且禁止重叠。
- 未覆盖时间自动使用旧默认值。
- `unlimited` 在新旧路径都能正确工作。
- 未配置分时段的候选行为完全不变。
- 请求路径不查询分时段数据库、不判断时间段。
- 多实例不会同时执行刷新任务。
- 立即刷新在无任务时立即启动，有任务时直接返回执行中。
- 刷新开始和结束均有日志。
- 旧表没有任何结构变更。

## 12. 风险与处理

| 风险 | 影响 | 处理 |
|---|---|---|
| Redis 刷新失败 | 当前值暂时延迟生效 | 保留旧值，下一轮重试并记录日志 |
| 刷新任务耗时超过一分钟 | 下一时间点延迟 | 不补历史任务，完成后执行下一个整分钟 |
| 多实例同时刷新 | 重复更新、资源浪费 | 全局 Redis 刷新锁 |
| 旧实例仍在线 | 旧实例不识别分时段 | 全量升级网关后再开放配置 |
| 分时段配置删除后残留 key | 继续使用旧运行值 | 保存/删除时主动清理，并通过 TTL 兜底 |

## 13. 追踪矩阵

| 需求 | 功能模块 | 技术组件 | 验收标准 |
|---|---|---|---|
| 分钟级配置 | 管理页面、配置 API | 新配置表 | 时间段可保存且不重叠 |
| 不完整覆盖 | 后台有效值计算 | 分时段解析器 | 空白时间使用旧默认值 |
| 不受限 | 页面、Redis 解析 | `unlimited` | 新旧路径均可用 |
| 请求无时间判断 | 请求配置读取 | Redis Lua/Pipeline | 请求不查分时段表 |
| 多实例互斥 | 刷新调度 | Redis SET NX 锁 | 同时只有一个刷新者 |
| 立即刷新 | 管理接口 | 同一刷新锁 | 无任务立即启动，有任务返回执行中 |
| 旧逻辑兼容 | 旧表、旧 key | 回退逻辑 | 未配置候选行为不变 |
